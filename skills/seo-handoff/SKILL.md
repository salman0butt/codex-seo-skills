# SEO implementation handoff for Codex

Translate SEO findings into a practical implementation brief for a developer or site owner. Work only from supplied/verifiable facts. This is an original Codex-specific workflow, not a copy of the proprietary legacy Codex implementation.

## Inputs
Use a report, source code inspection, page observations, diagnostics, or user-provided exports. Document the data source, timestamp, scope, unknowns, and whether the finding was measured or inferred.

## Steps
1. Group each verified finding by affected URL/template/system, and deduplicate root causes.
2. Prioritize by observed impact, confidence, affected scope, effort, and risk. Put speculative opportunities in a separate validation backlog.
3. For each issue provide **finding**, **evidence**, **recommended change**, **owner**, **files or systems affected**, **acceptance criteria**, **verification method**, and **rollback**.
4. Include code-level paths and example patches only when the codebase is available. Never invent exact filenames in another system.
5. Separate advisory recommendations from authorized code changes; never deploy, submit indexing APIs, or modify external properties without a clearly authorized task.
6. Report any blocked Google Search Console/GA4/API data as unavailable rather than asserting success.

## Output
A concise prioritized issue table, a release or sprint plan, and a post-deploy checklist: crawlable status, expected canonicals, index directives, relevant JSON-LD validation, mobile experience, Lighthouse lab and CrUX field checks when available, and Google Search Console monitoring when authorized. Explicitly state that no ranking outcome is guaranteed.

## Private Google metrics handoff

For reports generated by `private_seo_report.py`, preserve provider-specific definitions and date windows. Describe GSC metrics as search-result interactions and GA4 metrics as site session activity; never equate them, sum per-day distinct users, or invent trends from a single period. Distinguish `no_data` and blocked API calls from measured zero. Do not embed a private property ID or personal identifiers in shareable tickets.

## Reproducible offline evidence handoff (Codex v0.7)

When the user supplies JSON evidence from `private_seo_report.py` and/or `quick_audit.py`, run `"${HOME}/.agents/skills/seo/scripts/codex-seo" run seo_report_builder.py --gsc-current <gsc.json> --quick-audit <page.json> --format markdown` (adjust supplied inputs). This is **offline and read-only**. It generates conservative prioritized tickets with source audit references, acceptance criteria and reproducibility steps. It does **not** execute suggested changes.

For prior/current exports, require the operator to verify matching property identity **before** passing `--confirm-same-property`. The tool also requires adjacent equal-duration periods. Explain GSC CTR as percentage-point changes and mean position as a noncausal numerical difference, not a guaranteed ranking gain. Refer to `docs/EVIDENCE_REPORTING.md` for privacy safeguards, synthetic examples and validation.

## Local history and optional replay templates (Codex v0.8)

For user-provided saved exports, run the offline `seo_history.py record --gsc-current <saved.json> --export-markdown` to preserve an idempotent private snapshot and handoff report. `seo_history.py list`, `show` and explicitly confirmed `prune` manage local history. The `seo_schedule_template.py` tool can **print** reviewed weekly cron/launchd examples, but never install them or make them fetch fresh Google data. See `docs/OFFLINE_HISTORY.md`. History compares private properties or ordered page audits only with explicit user/operator identity attestation; absence of a finding is not proof of correction.
